# NF Hybrid — Render deployment

## Release configuration

`render.yaml` creates **nf-hybrid-portal-production** and **nf-hybrid-production-db** in Frankfurt. This is a separate live deployment, with an empty PostgreSQL database, one owner and no sample members or classes. It does not require a persistent web-service disk.

The selected starting plans are web `0.5c-512mb` and database `0.1c-256mb`, with 1 GB database storage. Their listed compute prices are approximately **$13/month combined**, before any separately billed storage, bandwidth, taxes and SMS credits. Review the actual checkout total before creating resources. [Render pricing](https://render.com/pricing), checked 28 October 2026.

If a production service already exists, preserve its resource names and database identity. Do not apply a new-resource Blueprint to an existing member database without first reviewing the changes and taking a backup. Keep any existing demo separate.

## Before deployment

- The release branch must be available in `costas195/GroupTrainingWebsite`, with passing Portal checks.
- Your Render account must be connected to that GitHub repository and have billing enabled.
- Prepare the owner's real name, contact email, login username and initial password of at least 12 characters.
- Have the WebSMS key available privately and sufficient credits. The configured sender is **NF Hybrid**.
- Keep the local SMS key in its ignored file until it is entered directly into Render. It is not included in the release ZIP or Git.

## Create the production Blueprint

1. In Render, choose **New → Blueprint** and select `costas195/GroupTrainingWebsite`.
2. Select the release branch, currently `codex/production-launch`, and the root `render.yaml` file. Use the tested commit.
3. Review the new service and database names, Frankfurt region, plans and displayed cost.
4. Fill in the prompted private values: `OWNER_NAME`, `OWNER_EMAIL`, `OWNER_USERNAME`, `OWNER_PASSWORD` and `WEBSMS_API_KEY`.
5. Create the Blueprint after approving its cost. Render installs dependencies, runs `python manage.py init-db` and starts Gunicorn.
6. Wait for a successful deployment and a healthy `/health` response. Open the assigned HTTPS address and sign in with the owner username and initial password.
7. Confirm the portal has no sample members or classes. Remove `OWNER_PASSWORD` from Render after the first successful sign-in. Keep `SECRET_KEY` stable.
8. Complete the live verification below before inviting members.

The Blueprint waits for repository checks before automatic deployments. Its pre-deploy migration command and `/health` endpoint are configured in source. [Render Blueprint reference](https://render.com/docs/blueprint-spec).

## Environment variables

| Variable | Setting |
| --- | --- |
| `APP_ENV` | `production`, supplied by the Blueprint |
| `DEMO_MODE` | `false`, supplied by the Blueprint |
| `AUTO_MIGRATE` | `false`; the pre-deploy command owns migrations |
| `DATABASE_URL` | Supplied from the new database's internal connection string |
| `DATABASE_SSLMODE` | `require`, supplied by the Blueprint |
| `SECRET_KEY` | Generated by Render; preserve it between deployments |
| `GYM_TIMEZONE` | `Asia/Nicosia`, supplied by the Blueprint |
| `OWNER_NAME` | Initial owner's display name |
| `OWNER_EMAIL` | Owner contact email |
| `OWNER_USERNAME` | Initial login name: 3–32 Latin letters, digits, periods, hyphens or underscores |
| `OWNER_PASSWORD` | Initial password, at least 12 characters; remove after first sign-in |
| `SMS_PROVIDER` | `websms`, supplied by the Blueprint |
| `WEBSMS_API_KEY` | Enter the existing key privately in Render |
| `WEBSMS_SENDER` | `NF Hybrid`, supplied by the Blueprint |
| `PUBLIC_BASE_URL` | Initially omit: the app uses `RENDER_EXTERNAL_URL`. For a custom domain, set its HTTPS origin without a path, query or fragment |

The first-owner values initialize a new database once. Later migrations preserve that account, including username changes. `manage.py init-db` prints owner usernames for upgrades from older releases; it never prints passwords. New secret variables with `sync: false` must be entered manually when updating an existing Blueprint. [Render secret configuration](https://render.com/docs/configure-environment-variables).

`RESEND_API_KEY` and `INVITE_FROM_EMAIL` are optional compatibility settings for the legacy email invitation API. They are not needed by the current SMS account flow. Local JSON or `.env` files are not production configuration.

## Startup and privacy checks

Production refuses demo mode, a missing PostgreSQL URL, disabled database encryption in transit, a missing stable session secret, missing SMS configuration, and databases containing demo accounts. Secure cookies, CSRF checks, role checks, trusted host validation, login throttling and session revocation remain enabled. The login page has no promotional sections; robots instructions and response headers discourage indexing. These do not replace authentication.

Render's managed PostgreSQL storage and backups use AES-256 encryption at rest. The application also requires TLS for database connections. Personal and temporary passwords are stored only as salted scrypt hashes. Local SQLite development files are unencrypted. [Render encryption](https://render.com/docs/postgresql-creating-connecting#encryption).

Never enable request-body tracing, credential payload logging or analytics that capture password forms or activation fragments. API responses use `Cache-Control: no-store`.

## Live verification

1. Confirm `/health` returns `{"status":"ok"}` and the website uses HTTPS.
2. Sign in as owner, create a class, refresh and redeploy once. Confirm the owner and class survive.
3. Create one controlled member using a phone you control. Confirm receipt of the generated username and temporary password, the **NF Hybrid** sender and the credit charge.
4. Sign in as that member. Confirm the mandatory password-change screen survives refresh and blocks access to bookings until completion. Choose a personal password and confirm the temporary password can no longer sign in.
5. Assign a membership month, test a booking and cancellation on phone and desktop, and confirm Cyprus session times.
6. Change the username as the member, then as owner. Confirm the ID, memberships, bookings and progress remain attached to the same account.
7. For a separate unactivated test account, resend initial credentials. Confirm earlier temporary credentials stop working.
8. Enable Render deploy-failure notifications and an external uptime check on `/health`. Agree a support contact, booking rules and a process for account access problems.

The earlier provider test was received successfully with sender HYBRID. The updated **NF Hybrid** sender and full invitation flow must still be verified from the deployed service. Automated tests mock provider delivery and incur no SMS charges.

## Backups, upgrades and recovery

Keep production in its own managed database. Before a schema change, create an export, store it privately and rehearse restoring it into a separate database. Verify sign-in and bookings against the restored copy. An actual Render restore rehearsal remains a launch task. [Render recovery and backups](https://render.com/docs/postgresql-backups).

Migrations 001–003 are versioned and additive. The username migration preserves existing numeric IDs, password hashes and relationships. The app refuses databases newer than its code. A previous application release may not accept a newer schema: plan compatible rollbacks before deployment. Never treat an application rollback as a database restore.

For a database incident, recover into a new database, validate its data, update `DATABASE_URL`, redeploy and verify access before resuming use. The Blueprint blocks public database connections; use Render's supported private access and backup tools.

## Release checks and remaining scope

See [README.md](README.md) for local commands and [docs/launch-checklist.md](docs/launch-checklist.md) for the release record. GitHub Actions uses Python 3.12 and PostgreSQL 17, validates both Blueprints, runs the business-rule suite, checks JavaScript, validates Gunicorn configuration and builds the release ZIP.

This release supports a controlled pilot. Recovery of forgotten passwords for already activated accounts, verified delivery callbacks, automatic retries, scheduled reminders, payments, recurring timetables, waitlists and separate coach roles are not implemented. Initial credential resending only supports unactivated accounts. Resolve account-recovery support before a broad rollout.
